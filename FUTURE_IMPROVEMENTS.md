# Future Improvements — TG Football

## 1. Alembic migration required for FK `ondelete` changes (DO before/with deploy)

These model FKs gained `ondelete='CASCADE'` at the ORM level. MySQL needs an
`ALTER TABLE` for the DB-level constraint to actually exist — the model change
alone does NOT alter an existing table.

- `database/models/duel.py` — `duels.user_1_id`, `duels.user_2_id` → CASCADE
- `database/models/statistics.py` — `stats.character_id` → CASCADE
- `database/models/payment/payments.py` — `payments.user_id` → CASCADE
- `database/models/christmas_reward.py` — `christmas_reward.user_id` → CASCADE
- `database/models/league_fight.py` — `clubs.id` FKs → RESTRICT (already in code)

On deploy:
```bash
alembic revision --autogenerate -m "fk ondelete constraints"
alembic upgrade head
```
Review the autogenerated migration before applying (autogenerate may not detect
`ondelete` changes on all MySQL/SQLAlchemy combos — add the `op.drop_constraint`
/ `op.create_foreign_key` by hand if the diff is empty).

## 4. Chronic Telegram network instability on the VPS (NOT fixed)

Prod VPS `46.202.190.222` (`football-blitz.online`, NAT64/IPv6) has had
constant `TelegramNetworkError: Request timeout`, `TelegramRetryAfter: Flood
control exceeded on getUpdates`, and `Bad Gateway` for months (see
`error_logs.log`, 19 errors on 2026-06-30 alone). Once the bot is *past*
startup, aiogram retries getUpdates and it survives — but a fresh **startup**
during a bad-network window crashed the process (`bot.delete_webhook` timeout
→ unhandled → systemd restart loop).

- **Fixed (2026-06-30):** `start_polling()` in `main.py` now retries
  `delete_webhook` 3× then proceeds regardless, so a startup timeout no longer
  crashes the bot.
- **Still unguarded:** `start_utils()` makes Telegram calls at startup that
  are NOT wrapped — a timeout there could still crash startup. Wrap the
  startup broadcast/Telegram calls (or raise the aiohttp session timeout) for
  full restart-resilience.
- **Root cause to chase:** why getUpdates hits flood-control / timeouts so
  often — likely the VPS NAT64 egress or an aiohttp connector/timeout config.

## 5. `SchedulerAlreadyRunningError` at startup

`error_logs.log` showed 2× `SchedulerAlreadyRunningError` — some scheduler
class calls `.start()` on an already-running shared `AsyncIOScheduler`
(e.g. the class-level `scheduler` in `schedulers/scheduler_education.py`).
Non-fatal (bot ran 11 days). After disabling the 3 promo schedulers the count
dropped to 0, but the shared-instance pattern remains. Lower priority.

## 6. 13+ independent `AsyncIOScheduler` instances

Each scheduler class spins up its own `AsyncIOScheduler` + `.start()`. Works,
but is wasteful and is what makes `id`/`replace_existing` dedup impossible
across schedulers. Consider one shared scheduler injected into each class.

## 7. local repo ≠ prod (deploy hazard)

On 2026-06-30 `load_utils.py` md5 differed between local and
`root@football-blitz.online:/root/footballgame/` — prod had changes not in the

## 9. Duplicate-character pileup FIXED (2026-07-05) + follow-ups

Client reported "команда создание не работает и база пустая". Root cause was NOT
an empty DB (prod `football_bot_v2` was healthy: 830 chars / 198 users, 40 clubs,
at head). It was **duplicate characters**: ~11 rows per `characters_user_id` with
no UNIQUE constraint, so `CharacterService.get_character` (`scalar_one_or_none`)
raised `MultipleResultsFound` and crashed `get_club_text` → every club view
(create team / Моя команда / club list) died. Club id 40 *was* created; only the
render crashed.

**Fixed:** dedupe to 1 char/user (kept club-holder → most exp/money → lowest id;
626 shells + FK children deleted, backup `football_bot_v2_prebackup_2026-07-05_1509.sql.gz`);
`get_character` now `order_by(...).limit(1).first()` (can't crash on a stray dup);
`create_character` is get-or-create; migration `af10341a0261` adds
`uq_characters_user_id`; `deploy/restart_server.sh` now runs `alembic upgrade head`
before restart (schema can't lag code again); `utils/schema_guard.py` logs a
startup drift canary.

**Follow-ups (deferred, not blocking):**
- `database/session.py` `get_session()` swallows exceptions without re-raising —
  a silent-failure risk for other write paths. Harden separately.
- 6 orphan characters with `characters_user_id IS NULL` left in place (harmless:
  UNIQUE allows NULLs, `get_character` never matches them). Clean up if desired.
- Origin of the dupes was a repeated bulk event (id-clustering), now impossible
  via the UNIQUE constraint regardless of source.
